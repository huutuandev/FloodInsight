# Flood data sources and readiness for Da Nang

Research and acquisition checks dated November 25, 2026. The study area is the original five FloodInsight monitoring points in the urban core. The points retain their existing identifiers, name labels and WGS84 coordinates. A point lookup, grid cell or neighborhood statistic provides no district-wide observation coverage.

## Data model, evidence rules and readiness

Alembic 0005 adds five tables. `flood_dataset_assets` links the existing `data_sources` registry to source URI, checksum, receipt time, method, licence and attribution. `flood_events` stores a source-specific event key and documented time interval, original locality and boundary vintage. `flood_observations` holds point evidence with optional event and canonical location links, UTC-aware observation instant, WGS84 coordinates, uncertainty radius, evidence reference, quality grade, and optional original locality/boundary vintage. `flood_terrain_features` stores persistent point covariates. `flood_hydrology_observations` stores validity, requested point and returned grid, units and asset provenance. A separate offshore station is independent of the five urban locations.

- **Flood confirmed** requires traceable evidence intersecting the observation’s coordinates or defensible uncertainty footprint at the observed time. A city or ward event report alone supports an event record.
- **Non-flood confirmed** requires affirmative observation of dry or baseline conditions under documented valid spatial and temporal coverage, e.g. a clearly observed camera field or verified sensor coverage. The DB rejects the label without coverage evidence. Quality review must still establish what that evidence means.
- **Unknown** covers gaps, ambiguous pixels, masked built-up areas, unavailable cameras, unresolved geocoding or time, and all periods with no report. Unobserved periods can remain absent from the table. A negative training label may never be inferred by joining for missing event records.
- Preserve the jurisdiction as reported. The 2022 event stores the then-reported Đà Sơn, Hòa Khánh Nam, Liên Chiểu, Đà Nẵng hierarchy. The 2025 administrative reorganization makes present-day jurisdiction joins date dependent. Historical boundary geometries and authoritative crosswalks remain to be acquired. [Provincial resolution](https://congbao.chinhphu.vn/van-ban/nghi-quyet-so-202-2025-qh15-45050.htm), [Da Nang commune/ward resolution](https://chinhphu.vn/?classid=2&docid=213991&pageid=27160)

**Readiness.** No supervised flood dataset is available. The Phase 1 tables support a point-level susceptibility study using explicit feature coverage and data-age flags. Keep static surface features separate from short-term rainfall, antecedent soil moisture and offshore water levels. Align environmental data by validity and actual receipt; keep forecast/retrospective features distinct and reconcile datum and river/urban hydraulic connectivity before combining elevation and water level. A later index can use documented, sensitivity-tested ranks of relief, antecedent rain, soil wetness, surface cover and validated drainage proximity. Show missing components and abstain where the specified coverage is insufficient. Index values would be relative indicators, without probability or flood-depth interpretation.

## Reproducible commands

Run from the repository root with the existing Compose environment configured. Use a separate project and a free `POSTGRES_PORT` for an isolated demonstration. Existing database operators can omit the test project name after confirming their target database and backup.

```powershell
docker compose -p floodinsight-phase1 up -d --wait postgres
docker compose -p floodinsight-phase1 build warehouse-service warehouse-migrate
docker compose -p floodinsight-phase1 run --rm --no-deps warehouse-migrate
docker compose -p floodinsight-phase1 run --rm --no-deps warehouse-service python -m floodinsight_warehouse.flood_data ingest elevation
docker compose -p floodinsight-phase1 run --rm --no-deps warehouse-service python -m floodinsight_warehouse.flood_data ingest soil-moisture --start 2023-10-13 --end 2023-10-13
docker compose -p floodinsight-phase1 run --rm --no-deps warehouse-service python -m floodinsight_warehouse.flood_data ingest coastal-sea-level
docker compose -p floodinsight-phase1 run --rm --no-deps warehouse-service python -m floodinsight_warehouse.flood_data ingest official-events
docker compose -p floodinsight-phase1 run --rm --no-deps warehouse-service python -m floodinsight_warehouse.flood_data audit
docker compose -p floodinsight-phase1 run --rm --no-deps -v "${PWD}/services/warehouse-service/tests:/app/tests:ro" warehouse-service python -m unittest discover -s tests -p test_flood_sources.py
```

Append `--dry-run` to validate the response and show source coverage without accessing PostgreSQL. Soil moisture accepts up to 31 complete **UTC** dates per call and records provider grid coordinates. Coastal sea level requests the current provider UTC day and records validity without inventing model issuance. Point/range requests validate units and timestamps, retry transient transport/HTTP failures, skip null measurements and preserve genuine zeros. Database writes are transactional and replay uses asset and measurement uniqueness. Hydrology stores changed values as distinct evidence; identical values with the same source/grid/point/validity are reused. Separate retrievals with identical content do not overwrite the original receipt. Keep provider responses or GIS tiles externally if a later audit needs the complete original payload. API checksums exclude volatile provider processing duration; the official reference hashes curated metadata; raster checksums hash supplied file bytes.

Optional raster commands download the verified tiles into a temporary local directory. Use the Phase 1 warehouse container with an ephemeral Rasterio install on its Python path:

```powershell
$tiles = Join-Path ([System.IO.Path]::GetTempPath()) "floodinsight-phase1-tiles"
New-Item -ItemType Directory -Force $tiles | Out-Null
$dem = "Copernicus_DSM_COG_10_N16_00_E108_00_DEM"
curl.exe -fL --retry 3 --max-time 90 "https://copernicus-dem-30m.s3.amazonaws.com/$dem/$dem.tif" -o "$tiles/dem.tif"
curl.exe -fL --retry 3 --max-time 90 "https://esa-worldcover.s3.eu-central-1.amazonaws.com/v200/2021/map/ESA_WorldCover_10m_2021_v200_N15E108_Map.tif" -o "$tiles/cover.tif"
docker compose -p floodinsight-phase1 run --rm --no-deps --user root -v "${tiles}:/tiles:ro" -v "${PWD}/services/warehouse-service/requirements-flood-gis.txt:/tmp/requirements-flood-gis.txt:ro" warehouse-service sh -c "apt-get update -qq && apt-get install -yqq --no-install-recommends libexpat1 && python -m pip install --no-cache-dir --target /tmp/flood-gis -r /tmp/requirements-flood-gis.txt && export PYTHONPATH=/tmp/flood-gis:/app && python -m floodinsight_warehouse.flood_data raster copernicus-dem /tiles/dem.tif && python -m floodinsight_warehouse.flood_data raster worldcover /tiles/cover.tif"
```

On Windows with a non-default Docker Desktop engine, the tested commands prefixed Compose with `docker -H npipe:////./pipe/dockerDesktopLinuxEngine`. The Phase 1 workflow neither starts the weather scheduler nor trains models.

## Weather coverage and quality verification

The original `floodinsight` Compose project had no containers or labeled volumes in the accessible Docker Desktop Linux engine. There was no pre-existing listening PostgreSQL endpoint on the configured loopback port. The older coverage and historical gap documented in `FLOODINSIGHT_PROJECT_CONTEXT.md` came from a previous environment and could not be independently checked here.

The existing `HistoricalPipeline` ran a bounded backfill and ETL for October 13, 2023 (Vietnam civil date) in the isolated `floodinsight-phase1` database. It loaded **125 raw observations, 120 hourly facts, 5 daily facts and 5 checkpoints**, with 24 valid rainfall hours per point, no partial days, no missing raw timestamps and no null rainfall, temperature, humidity or wind in the 120 facts. All five requests mapped to the ERA5 grid at **16.0° N, 108.25° E**. The payload contains requested point and returned grid separately. Vendor precipitation and liquid rain units are both millimetres. Raw validity ranged from October 12 17:00 to October 13 17:00 UTC, including the interval-ending boundary hour; data receipt occurred on November 25, 2026. This one-day sample establishes completeness within its window only. The soil-moisture import uses October 13 UTC, which is shifted seven hours relative to the Vietnam civil-day rainfall window.

The existing Forecast API client also validated **125 live snapshots in memory** (5 modeled-current and 120 hourly), with rain in mm and validity from November 25 13:00 UTC to November 26 12:00 UTC, 2026. The returned horizontal grids were 16.063269° N, 108.23864° E (Hải Châu); 16.063269° N, 108.15341° E (Thanh Khê and Liên Chiểu); and 15.992970° N, 108.22138° E (Cẩm Lệ and Ngũ Hành Sơn). This check did not persist forecast snapshots or enable the scheduler. Forecast response timestamps are validity and receipt, without a separate model initialization instant.

The operator `audit` command reads a repeatable PostgreSQL snapshot. It reports date gaps between stored days, partial rain days, hourly null counts, raw provider coordinates and units, validity and receipt bounds, historical checkpoint quality, flood asset/label/feature counts, and distinct hydrology hours and internal gaps. Zero gaps in this demonstration refer to one sampled interval.

Alembic reported `0005 (head)`. The five adapter tests passed. An attempted negative label without coverage evidence was rejected by the live PostgreSQL check, and the test transaction was rolled back. Each of the six imported source workflows replayed with zero inserts for identical input. The isolated PostgreSQL container was stopped to release the host port. Its Compose volume retains the dataset and can be reopened with the PostgreSQL startup command above. It contains no ML run or predictions.

**Remaining acquisition blockers.** Obtain dated, geocoded positive and affirmative dry observations with valid coverage windows. Acquire licensed municipal exports for stage, drainage and boundary versions. For waterways, use a time-stamped Geofabrik extract or an approved municipal network and validate feature geometry and tagging before calculating distances. For regional discharge and satellite-derived flood evidence, match modeled reaches or imagery footprints to point/zone geography and validate observability, coverage gaps and event timing before use. No river or drainage distance, discharge, gauge, historical coastal series or satellite label was imported in this phase.
